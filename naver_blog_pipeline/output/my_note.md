## HLS vs WebRTC: 다중 카메라 환경, 지연율 측정의 딜레마와 해결책

실시간 영상 스트리밍은 현대 웹 서비스와 AI 기반 시스템에서 필수적인 요소입니다. 특히 **다중 카메라 지연율** 최적화는 사용자 경험과 시스템 효율성을 좌우하는 핵심 과제입니다. HLS(HTTP Live Streaming)와 WebRTC(Web Real-Time Communication)는 대표적인 스트리밍 기술이지만, 여러 대의 카메라를 동시에 처리할 때 발생하는 지연율 측정은 예상치 못한 복잡성을 가집니다.

이 글에서는 다중 카메라 환경에서 HLS와 WebRTC의 지연율을 정확히 비교하기 위한 실험 과정에서 겪었던 문제점과, 이를 해결하기 위한 구체적인 최적화 방안을 공유합니다. 정확한 지연율 측정은 시스템 성능 개선의 첫걸음입니다.

## 기존 지연율 측정 방식의 문제점 분석

초기 실험에서는 다수의 카메라 탭을 순차적으로 열고 각 탭의 로딩 시간을 측정하여 TTFF(Time To First Frame)를 기록했습니다. 하지만 이 방식은 여러 가지 문제점을 야기하며 실제 지연율과는 거리가 있는 결과를 보여주었습니다.

### 순차적 탭 로딩으로 인한 지연율 누적 현상
카메라 탭을 하나씩 순차적으로 열 때, 각 탭이 로딩되는 데 약 1.5초씩 소요되었습니다. 이는 탭의 개수가 늘어날수록 전체적인 측정 시작 시간이 인위적으로 지연되는 결과를 초래했습니다.

> "탭당 1.5초씩 늦어지는 현상 발견, 페이지 로드 직후 HTML 내부에서부터 시간을 측정하는데 탭이 생성되는동안 브라우저 초기화 딜레이가 TTFF에 산입되어 수천 ms수준으로 기록됨."

이처럼 브라우저 초기화 딜레이가 TTFF에 포함되면서 실제 미디어 스트림 수신 및 디코딩 지연과는 무관한 수천 ms 수준의 오차가 발생했습니다.

### 크롬 브라우저의 백그라운드 탭 스로틀링 문제
크롬(Chrome)은 CPU 자원 절약을 위해 포커스가 없는 백그라운드 탭의 타이머, 네트워크 요청, 미디어 디코딩 속도를 강제로 제한합니다. 이로 인해 다음과 같은 현상이 나타났습니다.

*   먼저 생성된 카메라 탭들이 백그라운드로 밀려나면서 미디어 스트림을 수신하더라도 디코더가 멈춰있었습니다.
*   모든 탭 생성이 완료된 후에야 디코더가 활성화되어 영상이 재생되기 시작했습니다.
*   반면, 단일 카메라 측정 시에는 백그라운드 대기 오버헤드나 스로틀링의 영향을 전혀 받지 않아 정확한 측정이 가능했습니다.

이러한 문제는 다중 카메라 환경에서 HLS와 WebRTC의 진정한 성능 차이를 왜곡시키는 주된 원인이었습니다.

## 정확한 지연율 측정을 위한 실험 개선 방안

위에서 언급된 문제점들을 해결하고 **HLS vs WebRTC** 지연율을 보다 정확하게 비교하기 위해 다음과 같은 개선 사항을 적용했습니다.

### 미디어 재생 동시 트리거 도입
각 카메라 탭을 열 때 미디어를 즉시 자동 재생하지 않고 '준비 상태'로 대기시킵니다. 그리고 모든 탭의 생성 및 로딩이 완료된 시점에 파이썬 스크립트가 동시 재생 트리거를 보냅니다.

*   모든 탭이 포그라운드 상태와 유사한 조건에서 동시에 미디어 스트림을 시작합니다.
*   이때부터 TTFF를 측정하여 백그라운드 스로틀링으로 인한 오차를 최소화합니다.
*   이는 미디어 디코더가 모든 탭에서 동시에 활성화되도록 유도하여 정확한 지연율 측정을 가능하게 합니다.

### 비동기 동시 페이지 로딩 적용 (asyncio.gather)
탭을 순차적으로 여는 루프 방식 대신 Python의 `asyncio.gather`를 사용하여 모든 카메라 페이지를 동시에 열도록 변경했습니다.

*   `asyncio.gather`는 여러 비동기 작업을 병렬로 실행하여 전체 탭 로딩 오버헤드를 크게 줄여줍니다.
*   이로써 초기 페이지 로딩 및 브라우저 초기화 딜레이가 TTFF에 미치는 영향을 최소화합니다.
*   결과적으로 다중 카메라 환경에서도 단일 카메라 측정과 유사한 조건에서 지연율을 측정할 수 있는 기반을 마련합니다.
