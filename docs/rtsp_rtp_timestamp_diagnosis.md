# RTSP/RTP Timestamp Diagnosis

## Current AI Runtime Behavior

The current AI pipeline reads RTSP streams through OpenCV `VideoCapture`:

- `ai/streams/video_reader.py`
- `stream/rtsp_reader.py`
- `scripts/serve_ai_overlay.py`
- `scripts/run_rtsp_inference.py`

This path does not expose raw RTP timestamps or RTCP sender report timestamps to the AI code.

`FramePacket.timestamp` is generated locally as:

```text
frame_idx / fps
```

This is a stream-relative synthetic timestamp, not an RTP timestamp.

`capturedAtMs` is generated by `FrameMetadataBuffer.record_capture()` with the local AI host clock immediately after a frame is read:

```text
time.time_ns() // 1_000_000
```

This is useful for overlay synchronization and latency measurement inside the current system, but it is not the camera RTP timestamp and not the RTCP NTP-derived absolute frame timestamp.

## MediaMTX Timestamp Setting

MediaMTX does not use a documented `timestamp=true` RTSP URL query parameter for this repository's normal RTSP read path.

The relevant MediaMTX setting is enabled in this repository's MediaMTX configs:

```yaml
pathDefaults:
  useAbsoluteTimestamp: true
```

When enabled, MediaMTX preserves absolute timestamps from supported incoming protocols instead of replacing them with the MediaMTX system time. For RTSP and WebRTC, MediaMTX routes absolute timestamps through RTCP sender reports, which map an NTP timestamp to an RTP timestamp. A compatible RTSP client can compute frame absolute time from:

```text
frame_abs_timestamp = ref_ntp_timestamp + (frame_rtp_timestamp - ref_rtp_timestamp) / clock_rate
```

## Important Limitation

Turning on `useAbsoluteTimestamp` in MediaMTX is not enough for the current AI worker to use RTP timestamps.

The AI reader currently uses OpenCV, and the project code only receives decoded frames. It does not receive:

- packet RTP timestamp
- RTCP sender report NTP timestamp
- codec clock rate
- packet PTS/DTS with reliable RTSP sender-report mapping

To actually use RTP-derived timestamps in AI logs or MQTT payloads, the RTSP reader must move to a client/library that exposes packet timestamps and RTCP sender reports, for example:

- a small Go sidecar using `gortsplib`
- a Python reader based on PyAV/FFmpeg if it can expose the needed RTSP timing metadata in the deployed build
- an FFmpeg/ffprobe diagnostic path for offline verification

## How To Verify On GPU PC

Check current AI evidence timestamps:

```bash
grep -R "\[frame-sync\]" -n ai_runner.log runs/registered_cameras/*-overlay.log | tail -n 20
```

If these logs show `captured_at_ms`, those values are AI local capture times.

Check whether MediaMTX is configured to preserve absolute timestamps:

```bash
grep -R "useAbsoluteTimestamp\|timestamp=true" -n stream configs docker-compose*.yml docs || true
```

Check whether MediaMTX is running:

```bash
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Ports}}" | grep -i mediamtx
```

If MediaMTX is not running, start it with the configured file:

```bash
MEDIAMTX_CONFIG=stream/mediamtx.yml bash scripts/run_rtsp_server.sh
```

This repository now enables timestamp preservation in:

- `stream/mediamtx.yml`
- `stream/mediamtx.webrtc.direct.yml`

If another MediaMTX config is used, add or override this setting:

```yaml
pathDefaults:
  useAbsoluteTimestamp: true
```

Then use a timestamp-aware RTSP client to verify RTCP sender reports. OpenCV-based AI logs alone cannot prove RTP timestamp propagation.

## Decision Summary

- Current `capturedAtMs`: AI local wall-clock time.
- Current `FramePacket.timestamp`: `frame_idx / fps`.
- Current RTP timestamp usage in AI: none.
- `timestamp=true`: not confirmed as the relevant MediaMTX setting.
- Relevant MediaMTX setting: `pathDefaults.useAbsoluteTimestamp`, now enabled in the project MediaMTX configs.
- Required future work for real RTP timestamp use: replace or supplement OpenCV reader with a timestamp-aware RTSP reader.
