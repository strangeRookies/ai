# VLM & RAG Database: Schema, Indexing & Querying

This document outlines the database schema, entity mapping, pgvector indexing, and query optimizations for the semantic search feature.

---

## 1. Database Schema (PostgreSQL)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE alert_event_descriptions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    alert_event_id BIGINT NOT NULL REFERENCES alert_events(alert_event_id) ON DELETE CASCADE,
    source_asset_type VARCHAR(32) NOT NULL, -- 'CLIP' or 'SNAPSHOT'
    source_asset_key VARCHAR(512) NOT NULL, -- S3 object key
    representative_keyframe_count INT NOT NULL,
    status VARCHAR(32) NOT NULL, -- 'PENDING', 'PROCESSING', 'SUCCESS', 'FAILED', 'SKIPPED'
    vlm_json JSONB,
    vlm_description TEXT,
    description_embedding vector(768), -- Fixed length matching text-embedding-004
    deidentified_keyframe_keys JSONB, -- JSON array of S3 object keys
    vlm_model_name VARCHAR(128),
    embedding_model_name VARCHAR(128),
    embedding_dimension INT,
    prompt_version VARCHAR(32),
    error_message TEXT,
    retry_count INT NOT NULL DEFAULT 0,
    processing_started_at TIMESTAMP WITHOUT TIME ZONE,
    locked_until TIMESTAMP WITHOUT TIME ZONE,
    last_attempted_at TIMESTAMP WITHOUT TIME ZONE,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT unique_source_asset UNIQUE (source_asset_type, source_asset_key, prompt_version, vlm_model_name)
);

-- Partial HNSW index only indexing SUCCESS rows with non-null embeddings
CREATE INDEX ON alert_event_descriptions USING hnsw (description_embedding vector_cosine_ops)
    WHERE status = 'SUCCESS' AND description_embedding IS NOT NULL;
```

## 2. pgvector Dimension Configuration: Known Risks

| Approach | Pros | Cons |
|---|---|---|
| **Fixed Size `vector(768)`** *(MVP Default)* | - Strict type safety at DB layer.<br>- Highly optimized index sizes.<br>- Prevention of dimension size mismatches. | - Model migration requires schema alteration if dimension changes (e.g. from 768 to 1536). |
| **Unconstrained `vector`** | - High model flexibility.<br>- Supports any model (OpenAI 1536-dim, Gemini 768-dim, local 384-dim). | - Mismatched dimensions cause cosine operators to fail at query time.<br>- Index creation is more complex. |

We choose **`vector(768)`** by default as it matches `text-embedding-004` (Gemini) and ensures maximum query performance and type safety.

## 3. Optimized Search SQL Query

The search query uses standard `WHERE` + `ORDER BY` + `LIMIT` to avoid the overhead of `GROUP BY` and `HAVING` operations.

```sql
SELECT d.alert_event_id, d.vlm_description, d.vlm_json, d.deidentified_keyframe_keys,
       (1.0 - (d.description_embedding <=> CAST(:queryVector AS vector))) AS similarity_score
FROM alert_event_descriptions d
JOIN alert_events e ON d.alert_event_id = e.alert_event_id
WHERE d.status = 'SUCCESS' 
  AND d.description_embedding IS NOT NULL
  AND (1.0 - (d.description_embedding <=> CAST(:queryVector AS vector))) >= :minSimilarity
  AND (:excludeMock = FALSE OR d.embedding_model_name <> 'mock')
  -- Optional metadata filters:
  -- AND (:facilityId IS NULL OR e.facility_id = :facilityId)
  -- AND (:dateFrom IS NULL OR e.detected_at >= :dateFrom)
ORDER BY d.description_embedding <=> CAST(:queryVector AS vector)
LIMIT :topK
```
